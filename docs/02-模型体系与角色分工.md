# OpenCode 模型体系与角色分工

这一篇回答两个问题：

1. `opencode` 支持哪些模型与 Provider？
2. 这些模型在系统里分别承担什么功能？

要注意两件事：

- 这里讨论的是“当前仓库注册支持的模型”，不是今天互联网上所有可用模型。
- 这里讨论的“模型功能”，既包含模型家族的能力特征，也包含它们在 `opencode` 里的角色分工。

---

## 1. OpenCode 不是单模型系统

`opencode` 的设计不是只绑定一个模型，而是：

- `models` 层维护统一模型元数据
- `provider` 层适配不同厂商 API
- `config` 层决定当前各个 Agent 角色默认使用哪个模型
- `agent` 层在运行时把不同角色映射到不同 Provider 实例

因此，真正的设计单元不是“选择一个最强模型”，而是“给不同角色选合适的模型”。

---

## 2. 角色级模型分工

系统里至少有 4 个 Agent 角色：

| 角色 | 配置名 | 核心职责 | 典型要求 |
| --- | --- | --- | --- |
| 主编码代理 | `coder` | 理解任务、规划、调用工具、生成最终回答 | 推理强、工具调用稳定、上下文长 |
| 摘要代理 | `summarizer` | 把长会话压缩成可延续上下文 | 总结能力强、成本可控 |
| 子任务代理 | `task` | 做只读检索、定位文件、查找关系 | 便宜、快、检索导向 |
| 标题代理 | `title` | 给新会话生成标题 | 极低成本、短输出 |

这就是 Agent 工程里非常重要的一个原则：

不要把所有问题都交给同一个模型角色。

---

## 3. 模型元数据里到底定义了什么

`internal/llm/models/models.go` 中的 `Model` 结构定义了系统关心的核心字段：

| 字段 | 含义 | 工程作用 |
| --- | --- | --- |
| `ID` | 系统内部模型 ID | 配置、持久化、切换模型 |
| `Name` | 展示名 | TUI 显示 |
| `Provider` | 模型提供方 | 决定调用哪个 Provider |
| `APIModel` | 真正发给厂商 API 的模型名 | 适配不同平台 |
| `ContextWindow` | 上下文窗口 | 决定自动压缩阈值 |
| `DefaultMaxTokens` | 默认最大输出 | 控制成本与输出长度 |
| `CanReason` | 是否支持更强推理模式 | 决定是否启用 reasoning 配置 |
| `SupportsAttachments` | 是否支持附件 | 决定能否发送图片/二进制内容 |
| 成本字段 | 输入输出价格 | 用于会话成本统计 |

这说明 `opencode` 把模型当作“有运行时属性的工程资源”，而不是一个字符串常量。

## 4. Provider 层支持的模型来源

从代码注册来看，`opencode` 支持的来源包括：

- OpenAI
- Anthropic
- Gemini
- GitHub Copilot
- Groq
- Azure OpenAI
- OpenRouter
- xAI
- AWS Bedrock
- Vertex AI
- Local 本地模型

这意味着系统设计目标不是绑定某一家，而是构建统一 Agent 运行时。

## 5. 各 Provider 的功能定位

### 5.1 OpenAI

特点：

- 模型族完整
- 推理模型与通用模型并存
- 多模态支持较好
- 可通过 `ReasoningEffort` 做推理强度控制

在 `opencode` 里更适合：

- 主编码代理
- 复杂推理与工具编排
- 标题/摘要等辅助角色

典型模型家族：

- `gpt-4.1 / mini / nano`
- `gpt-4.5-preview`
- `gpt-4o / mini`
- `o1 / o1-pro / o1-mini`
- `o3 / o3-mini`
- `o4-mini`

功能理解：

- `GPT-4.1`：通用主力模型，适合主代理
- `GPT-4.1 mini`：适合 title/task 这类低成本角色
- `GPT-4.1 nano`：极致便宜，但更偏轻量
- `GPT-4.5 preview`：更强的语言与生成能力，但成本高
- `GPT-4o`：多模态与速度折中
- `o1/o3/o4-mini`：更偏推理型任务，适合复杂规划、难问题拆解

### 5.2 Anthropic

特点：

- 代码理解与长上下文对话能力强
- `Claude 3.7/4` 支持更强推理模式

在 `opencode` 里更适合：

- 主编码代理
- 长流程任务
- 大量文本上下文约束场景

已注册模型：

- `claude-3.5-sonnet`
- `claude-3-haiku`
- `claude-3.7-sonnet`
- `claude-3.5-haiku`
- `claude-3-opus`
- `claude-4-sonnet`
- `claude-4-opus`

功能理解：

- `Sonnet`：主力编码与推理
- `Haiku`：轻量低成本辅助角色
- `Opus`：高质量但更贵，适合少量高价值场景

### 5.3 Gemini

特点：

- 超长上下文
- 价格结构通常较友好
- 适合检索型和长上下文型任务

已注册模型：

- `gemini-2.5`
- `gemini-2.5-flash`
- `gemini-2.0-flash`
- `gemini-2.0-flash-lite`

功能理解：

- `2.5 Pro`：主代理、复杂问答、长上下文推理
- `2.5 Flash`：task/title 这类速度优先角色
- `2.0 Flash / Lite`：强调吞吐与成本

### 5.4 GitHub Copilot

特点：

- 是一个接入层，而不是单一模型
- 通过 GitHub API 暴露多家模型
- 对已有 Copilot 用户成本友好

在 `opencode` 里很关键，因为它影响默认模型路由。

已注册的 Copilot 模型包括：

- GPT-3.5 Turbo
- GPT-4
- GPT-4o
- GPT-4o Mini
- GPT-4.1
- Claude 3.5 Sonnet
- Claude 3.7 Sonnet
- Claude 3.7 Sonnet Thinking
- Claude Sonnet 4
- o1
- o3-mini
- o4-mini
- Gemini 2.0 Flash
- Gemini 2.5 Pro

功能理解：

- 它让 `opencode` 可以“借用 GitHub 提供的多模型入口”。
- 对使用者而言，Copilot Provider 的意义在于：统一账号体系下拿到更多模型选择。

### 5.5 Groq

特点：

- 速度快
- 很适合低延迟场景
- 某些模型成本较低

已注册模型包括：

- `qwen-qwq`
- `llama-4-scout`
- `llama-4-maverick`
- `llama-3.3-70b-versatile`
- `deepseek-r1-distill-llama-70b`

功能理解：

- 更适合强调响应速度的任务
- 对复杂代码编排不是唯一优选，但对辅助检索和高速问答有价值

### 5.6 Azure / OpenRouter / VertexAI / Bedrock / xAI / Local

这些 Provider 的意义，不是“能力完全不同”，而是：

- 企业接入要求不同
- 计费与合规要求不同
- 可用模型来源不同
- 部署环境不同

工程上意义重大：

- `Azure`：企业级 OpenAI 接入
- `OpenRouter`：聚合型多模型入口
- `VertexAI`：GCP 下 Gemini 接入
- `Bedrock`：AWS 下 Claude 接入
- `xAI`：Grok 系列
- `Local`：本地模型、私有部署、离线或近线环境

## 6. 默认模型选择逻辑

`internal/config/config.go` 里做了默认模型路由：

优先级大致看可用凭证：

1. Copilot
2. Anthropic
3. OpenAI
4. OpenRouter
5. Gemini
6. Groq
7. Bedrock
8. VertexAI
9. Local

这很能体现工程思维：

- 不是让用户每次手选
- 而是根据环境自动找“当前最容易跑起来”的可用模型

不同角色默认还会区分：

- `coder` 更偏主力模型
- `task` 更偏快模型
- `title` 永远限制到很小输出

---

## 7. 为什么标题代理和主代理不能用同一个模型策略

因为目标函数不同。

### `coder`

优化目标：

- 任务成功率
- 工具调用质量
- 长链路稳定性
- 推理质量

### `title`

优化目标：

- 快
- 便宜
- 输出极短

如果把所有角色都绑到同一个贵模型上，系统会：

- 成本不必要地升高
- 延迟增大
- 简单任务浪费高能力模型

这就是多角色模型分工的核心动机。

---

## 8. `CanReason` 在系统里的实际作用

这是 `opencode` 很关键的一个工程细节。

如果模型 `CanReason == true`，系统会视 Provider 不同开启不同策略：

- OpenAI / Local：可附加 `ReasoningEffort`
- Anthropic：对于 `coder` 角色可启用 think 策略

这说明系统不是简单“记录一个模型能推理”，而是把这个能力传递到 Provider 调用层。

换句话说：

模型能力元数据，最后会影响实际请求参数。

---

## 9. 附件支持对 Agent 有什么意义

`SupportsAttachments` 决定是否允许发送二进制附件，例如图片。

这在 Agent 工程里很重要，因为它决定系统能否做：

- 截图分析
- 图片理解
- 视觉调试
- 多模态输入

如果模型不支持附件，`agent.Run` 会直接丢弃附件，避免错误调用。

这是一种简单但实用的能力降级机制。

---

## 10. 成本字段为什么必须建模

很多 Demo 里都忽略模型成本，但工程里不行。

`opencode` 为每个模型记录：

- 输入成本
- 输出成本
- 缓存输入成本
- 缓存输出成本

然后在 Agent 运行后把 cost 记回 `session.Cost`。

这带来的价值是：

- 可以知道一次会话到底花了多少钱
- 可以比较模型切换前后的 ROI
- 可以为自动路由与预算控制打基础

资深 Agent 工程师一定要有这个意识：

模型不是抽象能力，而是有成本结构的运行资源。

---

## 11. 从 Agent 视角看，各类模型应该如何分工

下面是一个适合学习和落地的分工框架。

| 模型类型 | 更适合的 Agent 工作 | 不适合的地方 |
| --- | --- | --- |
| 大型高推理模型 | 主代理、复杂规划、困难修复 | 成本高、标题生成浪费 |
| 中型平衡模型 | 常规编码、一般工具编排 | 极难问题可能不够稳 |
| 轻量快速模型 | task/title/检索总结 | 不适合承担最终复杂决策 |
| 多模态模型 | 附件分析、截图理解 | 纯文本高强推理未必最优 |
| 本地模型 | 隐私敏感、私有部署、近端推理 | 质量与稳定性受部署影响 |

---

## 12. 一个资深 Agent 工程师应如何评价模型，而不是迷信模型

评价一个模型，至少看 8 个维度：

1. 代码推理稳定性
2. 工具调用结构化能力
3. JSON/schema 服从度
4. 长上下文抗干扰能力
5. 成本
6. 延迟
7. 多模态能力
8. 在特定 Provider 上的接入成熟度

这也是为什么 `opencode` 把模型抽象成一组元数据，而不是只记一个名字。

---

## 13. 资深工程视角下的关键结论

### 结论 1

不要问“哪个模型最好”，要问“哪个模型最适合这个 Agent 角色”。

### 结论 2

模型选择是系统设计问题，不只是产品选型问题。

### 结论 3

真正成熟的 Agent 系统，必须让模型选择、成本、能力、上下文窗口和推理控制一起进入统一抽象。
