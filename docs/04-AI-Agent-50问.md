# AI Agent 深水区 50 问：按 Google 级别系统设计与工程评审来回答

这 50 个问题不再追求“解释概念”，而是按一线大厂面试、架构评审、设计质询的标准来组织：

- 难点问题
- 经典问题
- 反例问题
- 复杂取舍问题
- 能直接追问到源码与系统边界的问题

回答都尽量落在 `opencode` 的真实实现上，而不是泛泛谈 Agent。

---

## 一、系统边界与核心抽象

### 1. 如果只能用一句话定义 `opencode`，它到底是什么系统？

它不是聊天 UI，也不是单纯的“模型壳”，而是一个以 `Session` 为状态边界、以 `Agent` 为控制循环、以 `Tool` 为执行平面、以 `Provider` 为模型适配层、以 `Permission` 为风险阀、以 `SQLite` 为持久化后端的终端型 Agent Runtime。

真正的关键词不是“LLM”，而是 `runtime`。因为它解决的是持续任务执行，而不是一次性文本生成。

### 2. 为什么说 Agent 系统的第一设计对象不是模型，而是状态机？

因为一旦系统进入多轮工具调用，它就天然成为一个状态机问题。`opencode` 至少隐式维护了以下状态：

- 会话是否存在
- 当前请求是否进行中
- 当前消息是否完成
- 当前是否处于 tool-use 循环
- 当前工具是否被批准
- 当前是否达到摘要阈值
- 当前 session 是否被取消

如果这些状态没有清晰边界，模型再强也会出现：

- 重复执行
- 不可取消
- 错误恢复困难
- UI 显示错乱
- 成本归因不清

`activeRequests`、`SummaryMessageID`、`FinishReason`、`PermissionRequest` 都说明 `opencode` 本质上已经是一个状态机系统。

### 3. `Session` 为什么比“对话历史数组”更高级？

因为 `Session` 在 `opencode` 里不是聊天容器，而是运行边界。它同时承担：

- 消息聚合边界
- 成本归因边界
- 摘要切换边界
- 取消边界
- 父子代理边界

一个简单历史数组无法表达这些系统语义。`Session` 是运行时对象，历史数组只是其中一部分数据。

### 4. 为什么 `Message` 必须结构化，而不能只存 markdown 文本？

因为 Agent 运行事实不只是文本。`opencode` 的消息部件里有：

- `text`
- `reasoning`
- `binary`
- `tool_call`
- `tool_result`
- `finish`

这意味着系统可以回答比“模型说了什么”更关键的问题：

- 模型具体请求了哪个工具
- 工具输入参数是什么
- 工具执行结果是什么
- 这轮为什么结束

这对回放、评测、审计、错误归因都至关重要。

### 5. 如果让你指出 `opencode` 最重要的一个抽象，不是 `Agent` 你会选什么？

我会选 `ToolResult`。因为真正把 Agent 从“会说”变成“会做”的，不是 tool schema，而是“工具结果能够再次进入推理循环”。

很多系统停在：

- 模型能调工具

但做不好：

- 工具结果如何结构化回注入
- 不同 Provider 如何吃回同一种 `ToolResult`

`opencode` 在 OpenAI、Anthropic、Gemini、Copilot Provider 里都做了这件事，这才让运行时闭环成立。

### 6. 为什么说 Agent 不是 MVC、也不是简单的事件驱动应用？

因为它同时具备：

- 事件驱动
- 状态机
- 控制循环
- 外部副作用执行
- 不可靠上游依赖
- 软实时交互

这比普通 Web CRUD 难得多。`opencode` 的 TUI 只是壳，真正复杂的是“模型-工具-状态-事件”耦合环。

### 7. 如果要把 `opencode` 用一句面试术语描述，你会怎么说？

“A session-scoped, tool-augmented, multi-provider agent runtime with structured message persistence, permission-gated side effects, and automatic context compaction.”

换成中文就是：

一个按 Session 组织、支持工具增强、多 Provider、多轮循环、结构化持久化、权限闸门和自动上下文压缩的 Agent Runtime。

### 8. 为什么“Agent = 模型 + 工具”这个定义是不够的？

因为它漏掉了 5 个现实世界里最关键的层：

1. 状态边界
2. 权限边界
3. 失败恢复
4. 观测与审计
5. 成本与资源约束

`opencode` 的价值就在于，这 5 层并不是附属品，而是主设计的一部分。

### 9. 一个成熟 Agent 系统，哪些东西必须是一等公民？

至少包括：

- Session
- Message
- Tool
- Permission
- Provider
- Cancellation
- Usage/Cost
- Memory compaction

`opencode` 已经把这些都显式化了，这就是它适合拿来学习工程的原因。

### 10. `opencode` 最大的“非显然设计点”是什么？

不是多模型，而是“子代理只读”。这是非常高级的系统边界设计。

它意味着作者没有把“多代理”理解成“复制更多主代理”，而是理解成：

- 主代理负责决策和副作用
- 子代理负责低风险探索

这会显著降低系统失控概率。

## 二、控制循环与完成判定

### 11. `processGeneration` 为什么是整个系统的真正核心？

因为它实现了 Agent 最本质的控制循环：

1. 读取历史
2. 创建用户消息
3. 请求模型流式生成
4. 收集 tool calls
5. 执行 tools
6. 把 tool results 再喂回模型
7. 循环直到模型不再要 tool

这不是普通的 request-response，而是 plan-act-observe-replan loop。面试时如果一个候选人看不到这一层，通常说明他只会用 Agent，不会设计 Agent。

### 12. 为什么“完成判定”是 Agent 系统最容易被低估的问题？

因为模型说“我完成了”不等于真的完成。

典型失败场景：

- 模型没跑验证就说修好了
- 工具失败但模型忽略
- 权限拒绝后模型仍然输出乐观答案
- tool result 不完整导致错误完成

`opencode` 目前主要依据 `FinishReason` 退出，这足够实用，但从严格工程角度看，未来仍可以更强：

- 针对某些任务强制验证
- 引入 completion evidence
- 将“工具失败但回答结束”标记为低置信完成

### 13. 如果模型不断进入 tool-use 循环不结束，会发生什么？

这是经典 Agent failure mode：无限动作循环。

`opencode` 当前没有在 `processGeneration` 里显式设置最大工具轮数，这意味着系统更多依赖：

- 上游模型的自我收敛
- 用户手动取消
- Provider / context / token 的隐式约束

这在工程上是可用的，但不是强鲁棒设计。面试里如果问“你会补什么”，答案应是：

- 每次请求的最大工具轮数
- 同类工具重复调用检测
- 进展度判断
- 无收益循环熔断

### 14. 为什么取消功能不能只取消 UI，而必须取消运行时上下文？

因为真正消耗资源的是运行中的 Provider 请求和 Tool 执行，而不是 UI 渲染。`opencode` 把 `cancelFunc` 存入 `activeRequests`，取消时直接打断上下文，这是正确方向。

如果只取消 UI，不取消运行时，会产生：

- 后台继续烧 token
- 写工具仍可能执行
- 成本继续累计
- 状态与用户感知不一致

### 15. `ErrSessionBusy` 背后解决的是什么工程问题？

它解决的是“同一 Session 并发进入多个主请求”的一致性风险。

如果没有这个约束，两个请求同时改写同一条消息历史，就会出现：

- 消息顺序错乱
- tool result 归属错误
- cost 统计混乱
- UI 展示不可解释

因此 `IsSessionBusy` 本质上是会话级串行化策略。

### 16. 为什么 Agent 系统里“谁拥有控制权”是核心问题？

在 `opencode` 里，控制权并不完全在模型手上：

- 模型决定是否调工具
- 系统决定是否允许该工具执行
- 系统决定何时取消
- TUI 决定何时触发摘要
- 配置决定模型与推理强度

这说明成熟的 Agent 不是 model-centric，而是 shared control system。

### 17. 为什么流式生成会让 Agent 设计更复杂？

因为你要在“消息尚未完成”的时候就处理：

- 内容增量
- tool call 增量
- thinking 增量
- 中途取消
- UI 实时刷新

相比一次性响应，流式系统引入了更多中间态。`opencode` 里 `streamAndHandleEvents` 正是专门处理这个中间态复杂性的函数。

### 18. 为什么“工具调用成功”不等于“Agent 推理成功”？

工具可能执行成功，但决策仍然错。典型例子：

- grep 找到了错误文件，但模型读错了上下文
- edit 成功改了代码，但改的是错误位置
- bash 执行成功，但验证命令不充分

所以 Tool correctness 和 Task correctness 是两层指标，不能混。

### 19. 如果你要给 `opencode` 增加一个“完成质量分级”，你会怎么设计？

我会把完成至少分成：

- `completed_verified`
- `completed_unverified`
- `stopped_by_permission`
- `cancelled`
- `tool_loop_exhausted`
- `provider_failed`

这样未来在 UI、日志、评测和回放里都能更细粒度判断完成质量，而不是简单 `done=true/false`。

### 20. 一个优秀候选人应该如何评价 `opencode` 的控制循环？

正确评价不是“它能循环调工具”，而是：

- 优点：控制循环简单直接，Provider 抽象清楚，ToolResult 回注入干净，工程上可落地
- 短板：缺少显式工具轮数上限、缺少 progress heuristic、缺少任务级验证语义

能同时说出优点和约束，才是系统设计视角。

## 三、工具系统、权限与副作用治理

### 21. 为什么 Tool schema 是接口契约，而不是 UI 展示文档？

因为它决定了模型的动作空间。一个 tool 的参数设计如果含糊，模型就会高频误调。`opencode` 的 `ToolInfo` 是给模型看的 API 契约，不是给人看的帮助文档。

所以面试中必须追问：

- 参数是否最小充分
- 是否容易被模型误填
- 是否有危险自由度过大
- 是否有可被滥用的默认值

### 22. 为什么 `bash` 是最强工具，也是最危险工具？

因为它把动作空间从“有限结构化操作”扩展到“几乎任意副作用”。一旦 `bash` 失控，系统的安全面就会指数级扩大。

所以 `opencode` 正确地把它接入权限系统。但更深一层的面试问题是：

- 是否该给 bash 做子命令白名单
- 是否该区分读命令和写命令
- 是否该限制网络/重定向/长命令

### 23. 为什么 `edit/write/patch` 三个工具都存在，而不是统一成一个“modify_file”？

这是典型的工具粒度设计问题。

保留多个工具的价值在于：

- 给模型更明确的动作意图
- 允许不同工具使用不同安全和历史策略
- 有利于观测模型偏好的编辑方式

但代价是：

- 工具选择复杂度上升
- 模型可能混用不当

这是经典的“少数强工具 vs 多个专用工具”的设计取舍题。

### 24. 为什么工具系统必须显式处理“权限被拒绝”？

因为用户拒绝本身就是系统状态的一部分。它不是异常噪声，而是业务事实。

如果权限拒绝只作为普通错误抛掉，系统会丢失：

- 用户真实意图边界
- 为什么动作没有发生
- 模型应该如何重规划

`opencode` 至少把拒绝显式传回；更高级的系统还应让模型理解“这不是工具坏了，而是权限边界到了”。

### 25. `GrantPersistant` 的根本价值是什么？

它是在用 Session 作为 trust boundary。

也就是说：

- 不是永久授权给整个系统
- 不是每次都重新问
- 而是在当前会话、当前路径、当前动作范围内复用授权

这是一种很好的中间态设计，兼顾体验与安全。

### 26. 为什么“工具正确率”通常比“模型回答质量”更能预测 Agent 成功率？

因为 Agent 的价值在执行。如果工具经常：

- 选错
- 传错参数
- 结果解析错
- 没有被正确喂回模型

那最终任务成功率一定差。

很多团队只看 final answer quality，这是错位指标。Agent 首先应该评估 action quality。

### 27. 子代理只读真的够吗？什么情况下会成为瓶颈？

它在安全和可控性上是优秀设计，但会在以下场景成为瓶颈：

- 需要并发执行多个安全修改
- 需要让子代理负责独立 patch lane
- 需要把任务拆分成可并行的实现块

所以更成熟的演进方向不是“让所有子代理都能写”，而是：

- 增加受限写代理
- 给不同代理分配不同路径 ownership
- 引入更严格的审计和合并规则

### 28. 如果你是面试官，会如何质疑当前 MCP 工具策略？

我会问：

1. `GetMcpTools` 的缓存粒度为什么是包级？
2. 如果会话期间 MCP server 状态变化怎么办？
3. 不同 session 是否应该看到不同的 MCP 工具集？
4. MCP tool 的权限和本地 tool 的权限模型是否统一？

这些问题没有标准答案，但它们能迅速区分“会接 MCP”与“懂运行时隔离”的候选人。

### 29. 为什么“工具调用历史”应该成为未来评测的核心资产？

因为它能支撑：

- replay
- 自动评估
- 失败聚类
- 工具成功率分析
- 路由优化

在 `opencode` 里，这方面已经有结构化消息与 tool result 日志雏形，但还可以更系统化。

### 30. 一个资深工程师如何评价 `opencode` 的 Tool 设计？

评价应分层：

- 好处：结构统一，Provider 无关，权限接入自然，子代理工具边界清晰
- 问题：强工具较少约束，缺少任务级工具 policy，缺少工具成功率与重试策略

这种评价方式比“工具挺全”高级得多。

## 四、上下文、记忆与压缩

### 31. 为什么“记忆”是 Agent 最容易被营销化、最容易被误解的概念？

因为很多系统把“把旧消息继续拼进去”叫记忆，把“做了个摘要”也叫记忆。

从系统设计上至少要区分：

- 短期工作记忆
- 会话历史
- 摘要记忆
- 长期知识记忆
- 用户偏好记忆
- 项目结构记忆

`opencode` 目前主要拥有的是：

- 会话历史
- 摘要承接
- 项目上下文文件

它还不是完整长期记忆系统。

### 32. 为什么摘要不是越早做越好，也不是越晚做越好？

太早做会损失细节，太晚做会让模型已经被噪声淹没。`opencode` 用 `95% contextWindow` 触发，是一种简单但合理的启发式。

更深层问题在于：摘要阈值其实应受任务类型影响。

例如：

- 调试型任务需要保留更多局部细节
- 规划型任务更适合更早抽象化

这就是 future work 的空间。

### 33. `SummaryMessageID` 这个字段为什么非常关键？

因为它把“摘要切换”从模糊概念变成了可追踪边界。

系统可以知道：

- 哪条消息是当前会话的摘要起点
- 后续构造消息历史时从哪里截断
- UI 里哪条消息是 summary

没有这个字段，摘要只能是“某段文本被插进去”，而不是运行时事实。

### 34. 为什么 Context 文件拼接既强大又危险？

强大在于可以把项目规则自动带进 Prompt。

危险在于：

- 可能包含过期约束
- 可能包含冲突规则
- 可能造成 prompt 污染
- 当前实现只读一次并缓存，运行中更新未必生效

这正是工程上“外部上下文注入”的经典难题：便利性和一致性难兼得。

### 35. 如果让你批评 `getContextFromPaths` 的现状，你会怎么说？

我会说它很实用，但还有明显演进空间：

- `sync.Once` 让上下文在进程生命周期内静态化，适合性能，不适合动态更新
- 缺少上下文优先级和冲突解决
- 缺少结构化标签，而不是纯文本拼接
- 缺少 token budget 管理

这是一个典型“当前实用、未来可演进”的设计点。

### 36. 为什么“按需读取文件”比“预先塞满仓库”更优？

因为 Agent 成功率通常不是由原始上下文量决定，而是由相关上下文密度决定。`opencode` 倾向于先给环境概况和目录信息，再通过工具读取具体文件，这是更健康的策略。

### 37. 长期记忆系统最容易犯的架构错误是什么？

是把所有记忆都做成同一种存储和同一种检索路径。

成熟系统应把不同记忆分层：

- 规范记忆
- 用户记忆
- 项目记忆
- 任务执行记忆
- 历史摘要

否则后面一定出现召回不准、污染严重、维护困难。

### 38. 如果你要给 `opencode` 加长期记忆，你不会先做什么？

我不会一开始就上向量数据库全家桶。我会先做：

1. 结构化 project memory
2. 用户偏好记忆
3. 工具调用经验统计
4. 摘要质量与召回效果评估

因为没有清晰记忆分类，直接上 embedding 往往只是把混乱向量化。

### 39. 记忆系统最核心的评测指标是什么？

不是“召回了多少条”，而是：

- 对当前任务是否真有帮助
- 是否降低了工具调用次数
- 是否减少了错误重试
- 是否没有引入错误偏置

换句话说，记忆系统必须用任务指标评估，而不是只用 IR 指标评估。

### 40. 资深候选人应该如何评价 `opencode` 的上下文架构？

正确评价是：

- 短期工作流设计合理：历史 + 环境 + 项目上下文 + 按需文件
- 自动摘要是务实方案
- 但长期记忆、动态上下文治理、上下文预算控制仍有很大演进空间

## 五、评测、可靠性、并发与系统演进

### 41. 如果一个团队说“我们的 Agent 很强”，你会要求看什么证据？

至少看 5 类证据：

1. 任务成功率
2. 工具正确率
3. 平均工具轮数
4. 成本与延迟分布
5. 失败模式分解

如果只给 demo，不给分布式数据和失败样本，那通常说明系统还停留在展示阶段。

### 42. 为什么 Agent 评测必须分层？

因为 final answer failure 只是结果层，原因可能在任意层：

- tool selection 错
- 参数生成错
- provider 转换错
- 权限拒绝未处理好
- 上下文压缩丢信息
- 模型完成判定过早

没有分层评测，你无法知道该优化哪里。

### 43. `opencode` 当前并发模型最大的保守点是什么？

它对主会话请求采用串行化策略，这提高了一致性，但降低了会话内并发吞吐。

这是正确的默认值，但如果未来要做更高吞吐：

- 需要任务级 DAG
- 需要路径 ownership
- 需要 tool-level conflict detection

否则并发写代码就是灾难。

### 44. 为什么“并行代理”远比“多开几个模型请求”难？

因为并行意味着你要解决：

- 状态一致性
- 写冲突
- 成本归因
- 合并策略
- 失败隔离

`opencode` 目前的子代理只读策略，本质上是在避免把自己推进这个高复杂区间，这其实是成熟的克制。

### 45. 如果你要设计 `opencode` 的下一代并行系统，第一原则是什么？

第一原则不是“更多并发”，而是“并发不能破坏可解释性”。

所以我会优先设计：

- 任务 ownership
- 子代理 write scope
- merge protocol
- rollback unit

再考虑吞吐。

### 46. Agent 系统最难处理的经典 bug 是什么？

我会选“表面成功、实际失败”。

也就是：

- UI 显示完成
- 模型给出自信答案
- 但工具结果其实暴露了失败信号

这类 bug 比 crash 更难，因为它会悄悄腐蚀信任。要解决它，必须把验证与完成判定做得更严格。

### 47. 为什么“经济性”是资深 Agent 工程师必须回答的问题？

因为现实里不是只追求成功率，而是追求单位成本下的成功率。`opencode` 已经有 `session.Cost`，这让它具备继续向：

- routing optimization
- budget-aware planning
- model fallback
- role-based cost allocation

发展的基础。

### 48. 如果让你用面试方式挑战 `opencode`，你会问哪 4 个最硬核的问题？

我会问：

1. 如果主代理在写文件前被取消，系统一致性怎么保证？
2. 如果 tool result 很长导致上下文爆炸，是否应该做 tool-result compaction？
3. 如果 MCP 工具在会话中途失效，Provider 和 Agent 如何恢复？
4. 如果多个子代理都指向同一文件，如何做 ownership 和 merge？

这 4 个问题基本能区分“会做 demo”与“能做生产系统”。

### 49. 如果你要把 `opencode` 进化成面向团队的生产 Agent，缺什么？

缺的不是更多模型，而是更强的治理层：

- 策略引擎
- 审计日志
- 更细粒度权限
- 任务与代理编排层
- 评测平台
- 回放与故障分析面板
- 组织级记忆与规范系统

也就是说，从个人 CLI 到团队生产系统，中间差的是 control plane。

### 50. 一个资深 Agent 工程师和普通使用者的根本差别是什么？

普通使用者问：

- 这个模型强不强？
- 为什么这次没修好？

资深工程师问：

- 控制循环怎么收敛？
- 副作用怎么约束？
- 状态边界怎么定义？
- 完成判定怎么设计？
- 失败如何分层归因？
- 成本怎么量化与优化？
- 这个系统在 10 倍任务规模下还能不能解释自己？

如果你能用这些问题重新审视 `opencode`，并能把答案落到具体源码与未来演进方案上，你已经进入 Agent 工程的深水区了。
