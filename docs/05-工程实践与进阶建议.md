# OpenCode 工程实践、经典难点与面试式设计题

这一篇不是总结，而是把 `opencode` 放到“资深 Agent 工程师设计评审”的坐标系里，专门讨论：

- 经典难点
- 复杂取舍
- 反模式
- 如何继续演进

---

## 1. 10 个最值得学习的工程判断

### 1.1 主代理可写，子代理只读

这是全仓库最值得学习的判断之一。它体现的不是能力不足，而是：

- 风险面最小化
- 上下文职责分离
- 并发复杂度延后

很多系统一上来就把多代理做成“每个都能写”，最后很快陷入不可解释的写冲突和状态失控。

### 1.2 会话级串行化优先于吞吐

`ErrSessionBusy` 说明设计者优先选择了：

- 一致性
- 可解释性
- 可取消性

而不是盲目追求“同一会话多请求并发”。这是合理的第一阶段选择。

### 1.3 自动摘要放在 UI 触发层，而不是模型自发层

这意味着上下文压缩是系统策略，而不是模型自觉行为。这样的好处是：

- 更稳定
- 更可控
- 更容易做阈值治理

### 1.4 模型能力由元数据统一建模

`CanReason`、`SupportsAttachments`、`ContextWindow`、`DefaultMaxTokens` 都放进 `Model`，这是优秀的运行时抽象，而不是简单配置表。

### 1.5 Provider 与 Agent 解耦

这让系统具备：

- 多模型演进能力
- 多厂商容错空间
- 配置驱动的角色路由

### 1.6 ToolResult 是一级事实，不是日志字符串

这是决定系统未来能否做：

- replay
- offline eval
- failure clustering
- routing learning

的基础。

### 1.7 Permission 作为服务，而不是散落在各工具内部

这使得安全策略可以独立演进，不会和 Tool 逻辑纠缠在一起。

### 1.8 历史持久化不等于长期记忆

`opencode` 没有混淆这两件事。它有会话持久化，有摘要承接，但没有假装自己已经完成了复杂长期记忆系统。

### 1.9 LSP 不是锦上添花，而是代码 Agent 的高价值增强层

它帮助系统从纯文本操作过渡到更可靠的代码理解和诊断。

### 1.10 观测链路已经具备雏形

`message`、`session`、`logging`、`pubsub`、`toolResults` 让系统具备进一步做：

- 可视化回放
- 执行树分析
- 错误归因

的基础。

## 2. 10 个经典难点，OpenCode 是怎么处理的

### 难点 1：模型并不可靠，系统如何收敛？

当前做法：

- 用工具循环推进
- 用权限阻止危险动作
- 用用户取消做兜底

还不够的地方：

- 缺少显式最大轮数
- 缺少 progress heuristic
- 缺少强制验证收尾

### 难点 2：多模型如何统一接口？

当前做法：

- `Provider` 抽象
- `Model` 元数据
- 每个 Provider 自己实现 message/tool 转换

这是标准且合理的设计。

### 难点 3：工具结果怎么回注入？

当前做法：

- 统一 `ToolResult`
- Provider 侧各自适配

这是闭环成立的关键实现。

### 难点 4：如何避免高风险动作直接执行？

当前做法：

- `permission.Request`
- TUI 审批
- 会话级持久授权

### 难点 5：上下文过长怎么办？

当前做法：

- 自动摘要
- `SummaryMessageID` 截断历史

### 难点 6：子任务如何并发又不失控？

当前做法：

- 子代理只读
- 单轮 stateless 调用

### 难点 7：如何记录成本？

当前做法：

- usage -> cost -> session.Cost

### 难点 8：如何让 UI 不和业务强耦合？

当前做法：

- `pubsub`

### 难点 9：如何支持取消？

当前做法：

- `activeRequests` + context cancel

### 难点 10：如何支持不同部署环境？

当前做法：

- 多 Provider
- 凭证驱动默认模型路由
- local / cloud / enterprise 多入口

## 3. 10 个仍未完全解决的深层问题

### 问题 1：工具循环是否可能无收益重复？

是的。当前没有显式 repetition detector。

### 问题 2：完成判定是否过度依赖模型？

是的。当前主要依赖 `FinishReason`。

### 问题 3：摘要是否会丢关键局部事实？

可能会。任何摘要都会压损信息。

### 问题 4：ContextPaths 的缓存是否过静态？

是的。`sync.Once` 提高性能，但不利于运行中变更。

### 问题 5：MCP tool 的缓存与隔离是否足够？

对单用户 CLI 足够，但对多租户/长生命周期运行时未必足够。

### 问题 6：Tool policy 是否过于粗粒度？

是的。当前更像 allow/deny，而不是精细策略图。

### 问题 7：是否缺少系统级 replay？

是的。已有材料，但没有完整回放面板。

### 问题 8：是否缺少分层 eval？

是的。现在更偏运行系统，而非评测系统。

### 问题 9：子代理是否没有 merge 协议？

是的。因为它目前只读，暂时绕开了这个问题。

### 问题 10：是否缺少任务级 SLA / budget 控制？

是的。目前已有 cost 统计，但还没有 cost-aware planning。

## 4. 10 个你在面试中可以反问系统设计者的问题

### 1. 为什么自动摘要阈值是 95%，不是 80% 或动态阈值？
### 2. 为什么主会话串行化，而不是 optimistic concurrency？
### 3. 为什么子代理是 stateless 的，而不是可持续协作的？
### 4. 为什么把审批放在 Tool 执行前，而不是模型规划阶段？
### 5. 为什么 `ContextPaths` 采用进程级缓存？
### 6. 为什么不做工具成功率统计来反向优化提示词和路由？
### 7. 为什么没有显式最大工具轮数？
### 8. 为什么 message persistence 里没有更强的 execution tree 抽象？
### 9. 为什么 cost 已统计，却没有预算约束？
### 10. 如果要从个人 CLI 演进到团队级系统，控制平面打算怎么设计？

这些问题都不是为了挑刺，而是为了看系统设计者是否真的理解运行时的中长期演进。

## 5. 如果你要继续做强 OpenCode，我建议的优先级

### P0：先补可靠性，而不是先补花哨功能

优先补：

- 工具轮数上限
- 重复调用检测
- 完成质量分级
- 更显式的验证语义

### P1：补观测与评测

- 工具成功率
- 失败模式分类
- replay timeline
- prompt/tool/result tracing

### P2：补记忆治理

- project memory
- user memory
- task memory
- summary quality eval

### P3：补并行编排

- 只读并行子代理
- 受限写代理
- ownership model
- merge protocol

### P4：补策略控制

- path policy
- command policy
- session budget
- model routing policy

## 6. 一套更像 Google 风格的设计回答模板

以后如果你面试中被问“设计一个 coding agent system”，建议按这个框架答：

1. 定义任务边界和用户面
2. 定义状态模型：session/message/request/tool-run
3. 定义控制循环：plan-act-observe-replan
4. 定义副作用边界与权限模型
5. 定义模型/Provider 抽象
6. 定义工具 schema 与执行层
7. 定义上下文与压缩策略
8. 定义失败模式和恢复策略
9. 定义评测、成本、观测指标
10. 最后再谈多代理和长期记忆

这个顺序的重要性在于：先把 runtime 讲清，再讲智能增强。`opencode` 很适合用来练这套表述。

## 7. 最终评价

如果从“资深 Agent 工程师训练材料”的视角看，`opencode` 的价值不在于它已经解决了一切，而在于它恰好处在一个很好的学习区间：

- 已经有真实运行时
- 已经有多模型与多角色
- 已经有副作用与权限
- 已经有摘要与持久化
- 已经有可观测性雏形
- 但仍然保留大量值得追问和改进的系统设计空间

这比一个过于简化的 demo 更适合学习，也比一个过于庞杂的生产系统更容易建立完整理解。
